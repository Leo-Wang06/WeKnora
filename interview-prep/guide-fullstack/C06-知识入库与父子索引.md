# C06 知识入库与父子索引：从上传文件到可检索片段

> 课程性质：核心；目标掌握：看懂链路、理解机制、设计与表达。
> 课程导航：[导学](../WeKnora/导学.md)；前置：[C04 上传队列与解析状态](C04-上传队列与解析状态.md)；上一课：[C05 内容安全与嵌入预览](C05-内容安全与嵌入预览.md)；下一课：[C07 混合检索与重排](C07-混合检索与重排.md)。
> 对应：B4；[面经 Q4](../WeKnora/面经.md#q4-文件传完以后怎样把索引和-wiki-后续任务做成可观察可恢复的流程)。源码基线：`d06733d4157736c0e0e7972d014f0f056d237bb0`；本课聚焦文件入库与文本索引，不把 URL、ASR 或图片分支当成所有文件的必经路径。

## 本课重点

用户上传文档时，同步响应的“知识已创建”与异步处理完成是两个不同承诺。当前代码先保存文件，再写 `pending` 知识记录并投递处理任务；投递失败会把记录改为 `failed`，但仍返回知识对象和 `nil` 错误，调用方需要读取解析状态，而非把创建成功解读成可检索。开启父子分块时，较大的父块保存上下文，较小的子块参与检索索引；索引不是分块数据库的完整复制。解析尝试、取消、覆盖写入之间还有状态检查，不等于队列投递一次就只会处理一次。

## 主链与职责

`文件上传 → 文件存储 → Knowledge(pending) 入库 → TaskEnqueuer 投递 → ProcessDocument 校验租户/解析尝试 → 转换为文本、规范化、图片处理 → 选择分块策略/父子分块 → processChunks 保存全部 Chunk → 对可索引子块建向量/关键词索引 → 更新处理状态与后处理任务`。文件服务拥有原始内容，知识仓库拥有解析状态，块仓库拥有段落和父子关系，检索引擎拥有索引；接口先返回知识 ID，后端 worker 异步推进。对于运行形态，[容器绑定](../../internal/container/container.go)按启动环境 `REDIS_ADDR` 是否非空选择 Asynq/Redis 与无 Redis 时的进程内执行器：**配置了 Redis 后发生连接故障，不会运行时自动切换 Lite**。

## 源码阅读

1. [创建文件知识：`createKnowledgeFromFile`](../../internal/application/service/knowledge_create.go)：先看 `SaveFile`、`persistKnowledgeForCreation`、`DocumentProcessPayload` 与 `Enqueue` 的顺序。文件已存但落库失败时，在允许清理的分支删除刚保存的文件；投递或序列化失败时调用 `markKnowledgeEnqueueFailed`，`return knowledge, nil`，原因是文件和记录已存在，不能当作从未创建。对应同文件 `markKnowledgeEnqueueFailed` 的状态字段和错误信息。
2. [任务执行：`ProcessDocument`](../../internal/application/service/knowledge_process.go)：载荷恢复执行租户、获取租户记录和知识记录，检查知识库与租户绑定，校验 `attemptSuperseded`、删除/取消/已完成状态，然后以 `access.WithKBTaskWrite` 授予这一 KB 的后台写范围。随后按文件类型转换、检查不允许的格式或缺失模型，规范化文本和 HTML 表格，再存图及生成 `sourceIndex`。重试计数取 Asynq 或 Lite 的 `TaskRetryMetadata`，不能把 Lite 当成“不重试”。
3. [策略解析：`resolveChainWithProfile`](../../internal/infrastructure/chunker/strategy.go)：`heading`、`heuristic`、`recursive`、空配置与 `legacy` 有明确分支；只有显式 `auto` 或未知策略才运行 `ProfileDocument` 和 `SelectStrategy`。因此“没填策略就自动判断文档结构”是错误口播，空值走 legacy，`recursive` 也是 legacy 别名。
4. [父子分块分支：`ProcessDocument`](../../internal/application/service/knowledge_process.go)：`EnableParentChild` 为真调用 `SplitParentChild`，将父块与子块及 `ParentIndex` 编成 `ParsedChunk`；否则普通 `Split`。两个分支最后都交给 `processChunks`。源码位置以 `eff.ChunkingConfig.EnableParentChild` 为定位，不要把父子索引描述为全局默认。
5. [写库与索引：`processChunks`](../../internal/application/service/knowledge_process.go)：先建立父块的相邻链和子块的 `ParentChunkID`，将父、子与必要的其他块写入数据库；`textChunks` 只挑 `ChunkTypeText`。`CreateChunks` 总会尝试执行，即便知识库不启用向量/关键词索引，原因是 Wiki、图谱和摘要也要读块；`kb.NeedsEmbeddingModel()` 且已解析模型时才创建子块/普通文本索引信息并调用 `BatchIndex`。索引文本组合文档标题、标题面包屑与块正文，父块不另建嵌入。

## 机制与边界

拿一篇长文档举例：父块保存一个完整章节，若干子块分别覆盖小段落。向量召回命中子块后，可用 `ParentChunkID` 回到父块补上下文，避免直接把整章当候选导致细节难命中。普通分块则设置文本块的前后邻接；父子模式主要使用父块关系，不给子块串同样的邻接链。后续检索如何取回父块见[C07](C07-混合检索与重排.md)。索引条件与落库条件相互独立：关闭向量/关键词索引仍写块，不代表知识库搜索一定可返回这些块。

异步执行关注三个竞态：其一，老任务在重解析后到达，`payload.Attempt` 与当前尝试比较，旧任务跳过，不应覆盖新一轮块与状态；其二，用户删除或取消后，写块前、索引前和索引后都有检查，删除分支会尽可能清理刚写的块/索引，取消分支保留已持久化内容但停止后续推进；其三，模型或索引写入可能失败，`BatchIndex` 的暂时性错误在仍有重试机会时向任务队列返回错误，最终失败时记录 `failed` 并尝试清理块/索引。这里是多存储组件协调和补偿路径，**不是一个覆盖文件、数据库与向量库的原子事务**；部分清理也可能失败。`ProcessDocument` 初始已完成状态直接跳过，重试同一尝试在写入前还会清理旧块与索引，都是抑制重复工作的措施而非 exactly-once 保证。

## 需要懂什么

“创建”和“可检索”属于两条时间线：创建 API 保存来源并登记任务，worker 完成解析、落库、索引后才可能被召回。前者成功不证明后者成功；入队失败甚至返回 `(knowledge, nil)`，需要前端显示状态与失败原因。父子索引解决检索粒度与回答上下文粒度冲突：子块小，适合匹配；父块大，适合补信息。它不改变所有块必须持久化这一事实，也不是给每个父块额外生成向量。重试/取消的正确性依赖不断从数据库与尝试跟踪器重新校验，而不能只相信最初排队时的载荷。跨租户任务还要用服务器加载的知识库校验 `TenantID` 与 KB 归属，执行租户本身并非无限写权限。

## 需要记住什么

复述主链：**先存文件与 `pending` 行，再投递；worker 校验租户、尝试与取消 → 转换/规范化 → 策略分块 → 所有块入库 → 仅可检索文本块建索引**。空分块策略是 legacy，显式 auto 才做结构画像。入队失败返回已有知识行但置 `failed`；Redis 与进程内 executor 是启动配置选择，不是连接故障自动回退。父块存 DB、子块可建索引，通过 `ParentChunkID` 回填上下文；详细检索见[C07](C07-混合检索与重排.md)，面试表达见[Q4](../WeKnora/面经.md#q4-文件传完以后怎样把索引和-wiki-后续任务做成可观察可恢复的流程)。

运行中介入与续流：换一个投递时机，换一条时间线

同一条正在流式回答的聊天，途中发送“补充：只比较前端实现”。选注入当前运行时，SSE 回执决定何时在当前回答里插入用户气泡；选当前结束后再说时，当前回答不在此处切开，前端等待下一条独立的 assistant 运行并接上它的流。下方切换两条示意时间线，辨认哪个是网络回执、哪个只是界面预览。

机制怎么工作

已有 Agent 回答仍在生成时，handleSteerMsg 为补充消息生成 steer_id，连同当前 expected_assistant_message_id 和 delivery 通过 POST /sessions/:id/steer 送出。inject 会立即放一个“待确认”的用户预览气泡；after 只保留待处理队列，不以预览冒充本轮已注入。HTTP 回应表示这次 steer 请求的处理状态，不等于当前 SSE 里已经出现了执行分界。 HTTP 与 SSE 可能交错到达，前端靠 steer_id 对齐；收到 user_message_injected 时才把用户消息放到此前的 assistant 内容下面，并建立后续 assistant 展示段。

关键不变量：屏幕上被切开的 assistant 是视觉分段，不是多条持久化 assistant 消息。新段可用 steer-cont-… 作列表键，却仍保存同一个 assistant_message_id，所以停止、恢复及后续事件归并必须使用 persistedAssistantId；协作状态也按这个真实 ID 汇集，同组快照忽略非递增的 revision，旧运行任务的终态不被后来同任务同 run_id 的更新倒写。after 的后续独立运行则寻找另一个未完成 assistant ID，再用 GET 接入那条流。两者不可混为一谈。

选择补充消息的投递方式

共同起点（示意）：用户已发起 POST /api/v1/agent-chat/:session，SSE 的 agent_query 已给出持久化 assistant ID A，当前回答仍在流动；这时输入同一句“补充：只比较前端实现”。只改变 delivery 与对应运行时机。 单击选项或用键盘方向键切换，无脚本、断网也可读。

场景 A｜运行还活着，当前轮接受注入

handleSteerMsg(delivery='inject') → 预览 → steerSession → SSE user_message_injected → forkAfterInjectedUser

  1. 原流在跑SSEagent_query 把真实 ID A 交给前端；此前已有 assistant 思考、工具或答案内容。
  2. 点“注入”界面 + HTTP本地创建 steer_id=S、记住预期 ID A；先显示 _steerPending 用户预览，再发 POST /sessions/:id/steer，delivery=inject。预览不意味着运行已经读到消息。
  3. 两个回执竞速HTTP / SSEHTTP 可先回 queued，也可在 SSE 注入回执之后才回；若状态是 already_injected，前端清理待确认状态。不能凭 HTTP 到达顺序判定气泡分界。
  4. 真正分叉SSE处理 user_message_injected(S)：复用已有用户预览或恢复历史里的持久化用户行，封口此前的 assistant 段，把用户行移到其下方，再创建后续 assistant 展示段；后续事件绑定到新段，队列移除 S。
  5. 同轮收尾SSE直到 complete 才把当前 assistant 轮标成完成；此前某段的 answer.done 只结束该答案段，不能当作整轮完成。

屏幕顺序：assistant 已输出段 → 插入的用户消息 S → assistant 继续段

身份关系：第一段 id=A；继续段 id=steer-cont-S（展示键），assistant_message_id=A（持久化消息）。不是另起一个 assistant ID。

效果：读者能在当前回答的前后片段之间看见插入的用户消息；前端按 steer_id 合并预览与 SSE 回执，而不是把预览和回执当两次注入；重放时优先复用历史行和已切段。

场景 B｜选择 after，留给下一次运行

handleSteerMsg(delivery='after') → 排队 → 当前 SSE complete → attachSteerFollowUp → GET continue-stream?message_id=B

  1. 原流在跑SSE当前 assistant 的持久化 ID 仍是 A，正在产生自己的答案。
  2. 点“完成后”HTTP为补充消息记下 steer_id=S、预期 ID A 和 delivery=after，发 POST /sessions/:id/steer。此选择不会调用注入预览，也不凭 HTTP queued 在本轮制造 user_message_injected 分界。
  3. A 正常收尾SSEcomplete 调用 onTurnComplete / flushSteerAfterTurn(A)。尚有未失败的队列项时，attachSteerFollowUp 开始查看消息列表，而不是把当前 A 的流硬切成新消息。
  4. 发现下一轮HTTP 列表前端寻找与 A 不同、未完成且未等待输入的 assistant B；按 B.request_id 找到下一轮已持久化的用户消息行，替换预览/补齐显示，再同步服务端待处理队列。
  5. 接上 B 的流HTTP + SSEstartStream({method:'GET', url:'/api/v1/sessions/continue-stream', query:B}) 接入 B；这里的 GET 是追上后续独立运行，不等于 A 因异常掉线后的重连。

屏幕顺序：assistant A 完成 → 下一轮的用户消息 S → assistant B 流式输出

身份关系：A ≠ B，B 有自己的持久化 ID 与 request_id。正常排队路径通过 GET 接入已可见的 B，不是再 POST 一次 A 的原始问句。

边界：如果 steer 接口给出 new_run，前端在原流仍活动时设置 awaitingIdleSend，等完成后才 sendMsg；已经空闲则直接正常发送。这是没有活跃运行可承接的回退路径，不要误讲成所有 after 都由前端再发一条 POST。

别把后续运行接入与掉线恢复混淆

上述 B 是上一轮完成后，对另一个持久化 assistant ID 接流。另一种情况是同一流尚未终结却异常关闭或 30 秒无心跳：只有前端已从 agent_query 收到持久化 assistant_message_id、尚无 complete/stop/error、当前流未被主动取消、非嵌入流且端点是 agent-chat 或 continue-stream，canReconnect() 才允许按原 assistant ID 改用 GET /sessions/continue-stream/:session?message_id=A 重试（最多 8 次）。恢复是附着到 A 的事件流，不是再提交一次可能已被接受的 POST 问题。首次握手的 401 刷新凭据重试另有专门逻辑，不应与已收 ID 后的异常续流混称。

前端证据只证明“何时发出请求、如何按回执展示、何时尝试接流”；页面不推断后端运行器何处读取注入队列、是否一定成功注入、内部持久化事务与失败恢复语义。若 SSE 没有对应回执，不能因为乐观预览就说注入已经发生。

记住这一点

注入看 SSE 分界、after 看下一轮 ID、掉线看原轮持久化 ID。 HTTP steer 回应与 SSE 回执可以乱序；“一个回答被视觉切成两段”仍只认同一个持久化 assistant 消息；只有已经拿到 ID、没有终结且非主动停止的异常断流，才改 GET 接原轮，绝不因网络中断重发已接受的 POST。

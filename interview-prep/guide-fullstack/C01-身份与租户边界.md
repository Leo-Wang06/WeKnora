# C01 身份恢复、空间切换与真正的授权边界

## 本课重点

场景不是“给请求加个 token”这么简单：用户刷新浏览器、加入新空间、切换工作空间或访问共享资源时，浏览器保存的用户和角色可能已经过期。要分清三层：**前端恢复并协调会话快照**，**请求携带当前身份与所选租户意图**，**服务器验证身份、解析租户与资源权限**。前端路由守卫隐藏菜单不能代表服务端授权；`X-Tenant-ID` 是请求目标，不是允许访问该租户的凭据。

## 主链与职责

首屏 `main.ts` 安装 Pinia 后，在有存储 token 时先请求 `/auth/me` 校准用户、成员关系和能力，再等路由就绪后挂载；组件复用 store 的状态。选择空间会清掉上一空间遗留的聊天模型、智能体、知识库选择。业务请求经 Axios 注入 Bearer、语言及已选的空间 ID；401 时受保护请求共享一次 token 刷新，重放至多一次。到服务器，认证中间件验证 JWT 或识别 API key、确定真实目标租户和角色，路由的 API-key 策略与资源层的知识库权限再逐层收紧访问。这里有两个所有权：浏览器负责“界面一致性与重试”，服务端负责“身份和授权的最终裁决”。

## 源码阅读

1. **首屏校准。** 读 [`bootstrap()`：先 `/auth/me`，再装路由与挂载](../../frontend/src/main.ts#L30-L60)；再读 [`refreshFromAuthMe()`、`ensureAuthMe()` 与 `applyAuthMeResponse()`](../../frontend/src/stores/auth.ts#L337-L408)。前者要求写操作之后得到更新的一次请求，后者让首屏重复读取共享在途请求；响应写回用户、空间和成员资格，不只是还原 localStorage。继续看 [`createSequencedRefresh<T>()`](../../frontend/src/stores/sequencedRefresh.ts#L18-L60)：`refresh` 排在旧请求之后，`share` 直接复用，`invalidate` 增加代际，让迟到响应失去写回资格，不意味着网络已经物理取消。
2. **空间切换。** 读 [`setSelectedTenant()` 与 `clearTenantScopedClientState()`](../../frontend/src/stores/auth.ts#L235-L287)：持久化当前空间，同时清除非按空间分桶的智能体、知识库、模型选择，防止新空间的输入框仍引用旧 ID。读 [`logout()`](../../frontend/src/stores/auth.ts#L445-L483)：清空存储、作废飞行中的 `/auth/me`，调用会话资源缓存清理，避免登出后老请求“复活”页面。
3. **发出请求。** 读 [`getCurrentLanguage()` 和请求拦截器](../../frontend/src/utils/request.ts#L66-L105)：已选租户每次附 `X-Tenant-ID`，Embed 鉴权请求不被本地 JWT 覆盖；再读 [401 响应处理](../../frontend/src/utils/request.ts#L125-L194) 和 [共享刷新与流式重试](../../frontend/src/utils/authRefresh.ts#L109-L188)：普通受保护请求最多重试一次，匿名或嵌入请求直接返回其自身错误；轮换式 refresh token 不宜让并发请求各刷各的。
4. **服务器裁决。** 读 [`Auth()` 入口](../../internal/middleware/auth.go#L116-L192)，再读 [`authenticateJWTUser()`](../../internal/middleware/auth.go#L231-L307) 与 [`resolveTargetTenant()`](../../internal/middleware/auth.go#L309-L378)：若头部存在，必须是正整数，用户必须可访问且租户存在；否则落到 JWT/home tenant，再尝试首个有效成员空间。无可用空间时身份类路由可继续，其余返回 `409 TENANT_REQUIRED`。路由权限看 [`APIKeyRouteAuthorizer` 的默认拒绝与能力策略](../../internal/middleware/api_key_gate.go#L56-L152)，具体知识库访问再看 [`HasKBGrant()` 和 `KBPermissions.Check()`](../../internal/application/access/context.go#L36-L94)。

## 机制与边界

普通路径：用户切换租户后，选择状态被清理，请求带明确的目标租户；服务器验证可访问性，按目标租户成员关系确定角色，再由具体接口或资源校验读写权限。异常路径：头部不是正整数返回 400；不能访问的租户返回 403；只有身份没有空间时，不能把所有业务请求默认放过。浏览器侧会话刷新失败应停在错误/重新登录分支，而不能凭旧 UI 角色自行放行。客户端路由守卫在 [`router.beforeEach` 的导航分支](../../frontend/src/router/index.ts#L265-L408) 只负责用户体验；直接调用接口仍由后端检查。

API key 是机器主体，不能拿用户界面显示的管理员角色代替其授权：服务器按 method+路由匹配能力，不在白名单的路由默认拒绝；工作空间 API key 的头部也不能切到其他空间，见 [`authenticateAPIKey` 的空间绑定](../../internal/middleware/auth.go#L449-L479)。共享智能体并不把源空间所有知识库都“借给”当前用户：[`WithSharedAgent()`](../../internal/application/access/context.go#L24-L34) 仅授予配置内的知识库读取范围；权限检查还要绑定 caller、KB ID、所属租户和所需级别，并重验 API key 的 KB scope。此层边界由后端维持，与前端缓存命中与否无关。

## 需要懂什么

**认证、租户定位、授权不可混为一谈。** Bearer JWT 证明是谁；`X-Tenant-ID` 表示要操作哪个空间；角色和知识库级 grant 决定能做什么。客户端存储可能陈旧、可编辑，因此清理旧选择解决误用和可用性，不能成为权限证明。**代际失效不等于取消 HTTP。** 并发 `/auth/me` 较早发起的结果在登出或更新后必须被拒绝写回；“要最新”的刷新排队与“首屏共用”的请求合并是两个不同语义。**逐级收窄不是重复检查。** 中间件给请求建立已校验身份与租户上下文，路由 API-key 门禁限制机器主体可调用的接口，资源操作再检查知识库所有权、精确授予与组织共享；任何一层都不应由 UI 菜单状态代替。

## 需要记住什么

- 主链：首屏 `/auth/me` → 选择空间清旧 ID → 请求附身份与目标空间 → 服务端解析目标空间／角色 → 路由与资源逐级授权。
- `refresh` 排在在途请求之后，`ensure/share` 复用；logout/invalidate 使迟到结果不能落库，但不保证已发请求被取消。
- **不把“路由进不去”说成“接口安全”**；`X-Tenant-ID` 不授予租户权限，API key 也不继承用户的 UI 角色。结合 [Q1](../WeKnora/面经.md#q1-为什么共享刷新令牌仍需区分会话数据与语言请求的竞态) 与 [Q2](../WeKnora/面经.md#q2-如何让普通页面与嵌入页面显示受保护内容但不混淆权限) 练习这三个层次的口头表达。

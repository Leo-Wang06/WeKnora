# C03 共享资源缓存：并发去重、写后刷新与语言快照

> 课程性质：核心；源码基线：`d06733d4157736c0e0e7972d014f0f056d237bb0`。  
> 课程导航：[导学](../WeKnora/导学.md) · 前置：[C01 身份与租户边界](C01-身份与租户边界.md) · [下一课：C04 上传队列与解析状态](C04-上传队列与解析状态.md)。  
> 对应：B1／[Q1 会话与请求一致性](../WeKnora/面经.md#q1-为什么共享刷新令牌仍需区分会话数据与语言请求的竞态)。

## 本课重点

对话输入栏、知识库列表和智能体编辑器可能同时读取知识库、智能体和模型；写入配置后，旧的在途 GET 又可能比刚完成的写操作晚到，把新值覆盖。把所有请求直接并发发出去造成重复；简单缓存又可能长期展示旧数据。这里的实现采用**保留上次快照供渲染、并发请求合并、代际失效防旧结果回写、写后强刷排队**。语言变化还会让同一个智能体列表请求得到不同的本地化名称，故不能仅以资源 key 判断快照是否可复用。

## 主链与职责

消费者调用 `useChatResourcesStore().ensureX()` → 对应 `createCachedResource` 决定共享在途请求或启动读取 → `createVersionedRequestCoordinator` 维护请求顺序与 revision，只有仍属于当前代际的响应可写入 Pinia ref → 组件读 ref 绘制旧快照/新快照。模型设置页已有新列表时调用 `replaceModels()` 直接落入 ref 并 `markLoaded()` 作废旧 GET；其他写后触发 `ensureX(true)`，若旧请求在途就等待其结束后另发新请求。智能体名称由服务端根据 Accept-Language 返回，因此请求开始时就记录 locale；如果用户中途切换语言，下一次读取要为新语言排一次请求。

## 源码阅读

1. **业务对象与展示。** 读 [`useChatResourcesStore()` 的资源 ref、`createCachedResource` 包装](../../frontend/src/stores/chatResources.ts#L26-L120)：知识库、智能体、模型等共用 store，`validKnowledgeBases` 另按配置过滤，并非后端成功返回的每个 KB 都可直接用于聊天。智能体 `listAgents()` 请求开始前采样 `locale`，随响应一起写入 `agentsLoadedLocale`；[语言 watch](../../frontend/src/stores/chatResources.ts#L54-L80) 在加载语言不等于当前语言时作废智能体快照。到请求层检查 [`getCurrentLanguage()` 与 `Accept-Language`](../../frontend/src/utils/request.ts#L66-L88)，理解为什么同一个列表 API 的载荷与语言有关。
2. **无 TTL 列表原语。** 读 [`createCachedResource<T>()`](../../frontend/src/stores/resourceCache.ts#L3-L59)：`ensure()` 没有在途请求时主动再取、在途时共用同一个 Promise；`ensure(true)` 保证获得旧请求之后的刷新；`invalidate()` 使 snapshot loaded 标志和旧响应作废；`markLoaded()` 保留外部已写入的新值并禁止旧响应再覆盖。这里“没有 TTL”并非完全无缓存：Pinia ref 仍留作渲染，`isLoaded()` 表示当前快照标记，不代表安全授权或数据永久新鲜。
3. **排队与版本控制。** 顺着 `createCachedResource` 进入 [`createVersionedRequestCoordinator<T>()`](../../frontend/src/stores/versionedRequest.ts#L14-L90)：`start()` 记录发起时 revision 与序号；`requestRevision === revision` 才执行 `apply(value)`；普通 `fetch()` 复用 `inFlight`，强制 `fetch(true)` 将 `forceTargetSequence` 推至当前请求之后。即使先前读失败，`forceQueue` 也会执行后继读取。`invalidate()` 是**逻辑取消旧结果**，并不真正 abort 已经发送的 HTTP。
4. **语言和按 key 快照。** 读 [`isLocalizedSnapshotUsable`、`shouldForceLocalizedRefetch`](../../frontend/src/stores/localizedResourceCache.ts#L10-L39)：仅当载入语言与 UI 当前语言一致才算可用；另一语言的在途请求不能当作下一语言的查询结果。然后读 [`ensureAgents()` 的判断与并行共享资源](../../frontend/src/stores/chatResources.ts#L149-L225)：不同语言在途时强刷排队；自己的知识库读取是必需的，附带的组织共享知识库查询失败被吞掉，避免一个可选来源连坐整个输入栏。过滤后的 creator 列表走页面专用请求，不混入通用快照。
5. **消费与失效。** 读 [`replaceModels()`、`prefetchChatInput()`、`invalidate()` 与数据变化订阅](../../frontend/src/stores/chatResources.ts#L231-L318)：预取常用资源是并行的；模型列表可由设置页直接替换；登出时清空 ref 和 key cache；agent/KB/model 数据变更触发针对性强刷。单条详情用 [`createKeyedSnapshotCache<T>()`](../../frontend/src/stores/resourceCache.ts#L61-L110) 按 key 保留快照直到显式失效、每 key 有自己的 revision，`null` 不落缓存，避免临时加载失败被永久固化。

## 机制与边界

设旧请求 A 正在读，用户完成写操作后要新状态 B：如果强刷直接复用 A，就可能在 B 落库前的快照上返回；如果 A 的响应在设置页已替换快照后返回，也可能覆盖 B。协调器先等待 A 结束，再启动下一序号的强制请求；直接替换时则增加 revision，使 A 即使返回也不再应用。普通组件同时挂载请求相同资源时，只共享在途 Promise；没有在途时下一次 `ensure()` 会重新请求，这与“60 秒内免请求”的 TTL 缓存不同。加载单个 KB 详情等高频按 key 查询的原语又是不同语义：有快照就复用，直到对该 key 明确失效。

语言交错也是典型时序问题：A 以 zh-CN 开始，用户改 en-US 后 A 完成，如果在 `await` 之后读当前语言标注，就把中文响应标成英文快照；源码将开始语言与响应配对，并在新语言请求时强制排队。需要注意实现边界：这些协调器解决**前端回写竞争**，不是服务器版本控制；存储在内存中的资源数据也不是可信权限。跨用户、跨租户或登出时必须走会话/空间失效路径，不能靠旧快照判断当前用户是否有访问权。

## 需要懂什么

**请求合并、缓存和版本互不等价。** 请求合并只减少同一时刻重复 IO；快照让页面先渲染旧值；revision 拒绝迟到写回；排队强刷保证写操作之后另发一次查询，分别处理不同的竞争。**语言是查询隐含参数。** 即使 URL 一样，`Accept-Language` 改变也意味着服务端返回可见文本不同；快照的可复用条件必须包含发起时语言。**局部失败不等于整体失败。** `ensureKnowledgeBases` 的主体请求出错应由调用方感知，附带的共享组织资源出错则保留上次快照；取舍服务于输入栏可用性，但不能把缓存当成组织共享的实时权限。

## 需要记住什么

- 常用列表：无 TTL、在途共用、写后强刷排队、旧 ref 先显示；详情：每 key 快照直到失效，不缓存 `null`。
- `markLoaded` 适用于外部已有新数据的场景；`invalidate`/revision 是拒绝旧响应回写，不是取消网络、也不是撤销服务端权限。
- 智能体本地化列表始终记录**请求开始时**的 locale。对照 [Q1](../WeKnora/面经.md#q1-为什么共享刷新令牌仍需区分会话数据与语言请求的竞态) 解释“读旧—写新—旧响应晚到”和“语言切换中请求晚到”两个时序例子。

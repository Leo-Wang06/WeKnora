## 本课重点

聊天界面收到的是**同一个执行任务持续追加的事件**，而不是“POST 成功后追加一段文本”。一次执行可能先给出持久化 assistant message ID，再输出文本、子 Agent 进度、工具审批请求、暂停/恢复与用户中途追加消息；网络断开之后应附着到已创建的任务继续读，而不是重新 POST 造成重复执行。本课要区分连接存活、文本片段结束、Agent 运行结束、待用户输入这四种状态，并看清前端组件与后端事件日志各自的责任。

## 主链与职责

用户发起对话 → `useStream` 用 SSE 接收有 `response_type` 的事件，绑定当前请求代际 → `useChatStreamHandler` 把事件归入 assistant turn 和子任务快照 → 提示卡在时间线/输入栏呈现，用户决策走独立审批接口 → 服务端恢复运行并通过流记录送出后续事件。中途 steer 可选择 `inject` 进入当前运行，或 `after` 排到本轮结束后另开运行；只有 `inject` 会先给用户待确认预览，收到真正的注入事件才将一个持久化 assistant 回合拆成多个视觉片段。当前运行断线由 `continue-stream` 重放同一条消息的事件；`after` 真正启动新运行时须寻找**另一条**持久化 assistant 消息，再以该 ID 附着。子 Agent 子流也从自己的消息列表与 continuation 重建，而不是靠父页面内存猜测其完成情况。

## 机制与边界

正常路径可看成“持久化回合 ID + 事件流水 + 多个投影视图”。父助手的一次 steer 插入后，UI 将旧 assistant 片段封口，在中间插用户消息，再建一个 synthetic ID 的续写片段；它们的 `assistant_message_id` 仍指向**同一条后端消息**。stop、续流与附件请求必须走 `persistedAssistantId()`，不能拿 Vue 用来区分气泡的 synthetic ID 请求后端。重放时先检查气泡已经夹在两个同回合片段中，避免双重拆分。

异常路径有四个不能合并的分支：一是首次 POST 尚无 assistant ID 时不能假定服务端已接受，也不能盲目重发；二是 ID 已收到、未完成时断线，改用 GET 附着并重放；三是 `after` 在上一运行完成后等待**新** assistant ID 再 GET，不属于旧消息的重连；四是审批后 `resume_pending_id` 对应的新片段尚未就绪，后端 409 表示时序未完成，而不是把旧片段的 complete 误认成审批后的执行结束。`run_suspended` 表示等待人参与，待办提示尚可操作；`answer.done` 只结束文本事件。服务端 steer 队列深度上限 10、请求长度上限 10000，消息持久化失败有限次重试；即使提及了新知识库或工具，中途 steer 也**不会扩大原运行的 KB、工具、技能授权范围**。

## 需要懂什么

**SSE 与任务执行不是同一件事。** 浏览器的 AbortController 能关闭这个客户端连接/终止其接收，不能据此证明后端任务已经停止；真正停止执行必须走服务端 stop 语义。**幂等恢复依赖可寻址的持久化 ID。** 初次 POST 建立任务，GET 只读取相同 message 的事件流水，因此心跳断线可追上进度，不能把重连写成“重新向模型提问”。**投影状态需要因果顺序。** 子任务 status 的 revision、run_id 和 pending prompt 的 pending_id 是避免旧事件或重放把新状态覆盖的键；时间线的视觉分叉不改变后端执行与权限主体。

## 需要记住什么

- POST 发起 → `agent_query` 给持久化 ID → SSE 事件投影 → 审批/用户注入分支 → `complete` 真正收束；断线后按同一 ID GET 重放。
- 不把 `answer.done`、`awaiting_input`、连接 `onclose` 说成 `complete`，不把前端的 steer 预览说成已被执行引擎采纳。
- generation + AbortController 解决旧连接误写界面；服务端会话/消息验证、事件日志和运行引擎决定真实状态。对照 [Q3](../WeKnora/面经.md#q3-断线后什么时候续接原答案什么时候跟随新一轮运行) 与 [Q6](../WeKnora/面经.md#q6-智能体连续执行时如何约束上下文与工具调用的权限) 回答“断线、审批、中途介入”三个追问。

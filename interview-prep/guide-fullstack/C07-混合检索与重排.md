# C07 混合检索与重排：从查询到带上下文的证据

## 本课重点

同一个问题可能需要语义向量和精确词项两种召回，但两个分数体系不能直接相加。`HybridSearch` 在权限和模型空间校验后，限制候选深度、一次计算查询向量、跨索引后端取回候选，再依据实际存在的召回分支选择“原分保留、关键词条件归一化或加权 RRF”。可选的 `HybridSearchWithRerank` 先保留较宽候选池，重排后才筛最终条数并扩展父块/邻块；普通 `HybridSearch` 不是“默认会调用重排模型”。问答流水线也有独立的重排插件，别混作同一入口。

## 主链与职责

`SearchParams/目标 KB → 校验所有 KB 权限与模型空间 → 限额并构建一次 query embedding → 按存储引擎和归属租户分组、并行召回 → 按检索器分类 → 单路去重或双路融合 → 主命中数量截断 → 回表取 Knowledge/Chunk → 按需补父块、相邻块和关系块`。若请求明确启用检索 API 的重排，则走 `HybridSearchWithRerank`：在融合与回表后让 rerank 模型评估更宽的候选，最后只对结果扩上下文。KB 服务负责可检索范围、分数和数据回填；模型服务负责查询向量、可选 rerank；知识块和索引的信息要靠 ID 再关联，不应把搜索引擎的候选当作完整知识文档。

## 源码阅读

1. [入口：`HybridSearch` 与 `hybridSearchCandidates`](../../internal/application/service/knowledgebase_search.go)：`normalizedMatchCount` 将未传或非正的 `MatchCount` 设为 `DefaultRetrievalTopK`，最大限制为 `500`；加载检索目标后先 `authorizeKBAccess` 再 `validateSameEmbeddingModel`，主 KB 必须确实位于本次 ID 集合内。过量取回深度按 `max(MatchCount*5, DefaultRetrievalTopK)*目标KB数` 算，并统一上限 `500`。缺少预计算向量且需要向量召回时只 embed 一次，`params.QueryEmbedding` 随后复用；按存储和租户分组检索后分类融合。选一个无向量索引的 KB 作混合目标主 KB 可能降级为仅关键词路径，故主 KB 的选取有语义。
2. [跨 KB 模型约束：`validateSameEmbeddingModel`](../../internal/application/service/knowledgebase_search_storegroup.go) 与 [模型身份：`ResolveEmbeddingModelKeys`](../../internal/application/service/knowledgebase_search.go)：比较模型名、基础地址和配置维度形成的身份，不把不同维度空间混合打分；解析后模型键为空的无向量 Wiki/图谱 KB 可参与目标集合而不改变有向量目标间的一致性检查；查询向量的实际维度也在 `GetQueryEmbedding` 中检查。若模型记录解析失败，键会回退为对应模型 ID，这只是兼容性兜底，不等于已证实两个向量空间完全相同。
3. [融合：`fuseOrDeduplicate`、`fuseWithRRF`、`bestRanks`](../../internal/application/service/knowledgebase_search_fusion.go)：仅向量时按 ChunkID 去重取最大分，保留原 cosine 分数；仅关键词时对**每条列表**做 `rescaleUnboundedScores`，只有本列表最大有限分 `>1` 才按最大值缩放，否则已有 `[0,1]` 分数不改；双路时按各列表内名次求 `vectorWeight/(k+vectorRank)+keywordWeight/(k+keywordRank)`，再除以理论最大 `(vectorWeight+keywordWeight)/(k+1)`。每条检索结果保持单独的名次列表，不能把并发完成顺序拼接后当排序。
4. [结果组装：`processSearchResults`、`collectEnrichmentChunkIDs`](../../internal/application/service/knowledgebase_search_results.go)：回表取命中知识与块，必要时取 `ParentChunkID`、相关和相邻块；额外块是回答上下文而不是另一遍被搜索模型打分的主命中。共享 KB 的读取需在权限授予基础上处理所有者租户的数据，不能只按调用方租户 ID 回表。
5. [显式重排入口：`HybridSearchWithRerank`](../../internal/application/service/knowledgebase_search_rerank.go)：未启用时直接走 `HybridSearch`；启用时先决议 rerank 模型，`topK` 默认取匹配数、最大 `500`，上调候选深度到 `max(topK, DefaultRetrievalTopK)`，先 `processSearchResults(..., true)` 禁止上下文扩展，重排并取 TopK 后再 `enrichRerankedResults`。指定的非法模型直接报参数错；自动发现不到模型、已选模型不可用或模型执行错误时保留检索顺序并写诊断，不代表“没有候选”或静默成功完成了模型重排。

## 机制与边界

示意：问题里既有产品术语也有语义同义表达，关键词命中具体术语，向量匹配相近语义；同一子块可能两路都命中。若向量排名第 2、关键词第 1，它的融合分是两项名次倒数的加权和，再按理论最高值缩放；一个只被向量召回的块仅有向量贡献。RRF 选择名次而非直接相加，因为余弦分和 BM25 的尺度不同；然而融合分不等价于“模型置信概率”，不能按它推断答案必然可靠。只走向量时保留原分，尤其 FAQ 匹配阈值需要原始相似度；只走 BM25 时仅在存在无界分数 `max>1` 时缩放，防止后续混合分/多样性计算被十几分的词项分数压满。

数量限制发生在不同阶段：候选取回上限 `500` 是控制底层查询负担，不是 API 永远返回 500 条；普通 `HybridSearch` 在融合后按请求 `MatchCount` 截断主命中。显式重排入口不能先按最终的 5 条截断再让模型排序，否则不可能把第 6～N 条提升进前 5。它用较宽候选集重排，然后对最终条目补上下文，避免为落选候选批量取父段。无可检索索引时按当前契约返回空集；跨 KB 无权限、模型空间不一致或存储失败要返回错误，不能把安全或配置故障误报成“搜索无命中”。跨租户共享知识先查调用者对每个 KB 的权限；切换执行租户只是执行数据查询的上下文，不授权读取该租户其他 KB。

## 需要懂什么

召回是**高覆盖率候选选择**，重排是**在候选内重新评估相关性**，上下文扩展是**把命中附近信息拿回来供回答**，三个阶段分别改变候选集、次序与证据展示范围。父块不参与索引不妨碍被取回：子块 `ParentChunkID` 是回表的桥梁。`HybridSearchWithRerank` 与问答插件的职责不能混淆：问答在 [C08](C08-动态问答流水线.md) 先通过 `HybridSearch` 拉取未扩展候选，后用 [流水线 `PluginRerank`](../../internal/application/service/chat_pipeline/rerank.go) 独立重排；检索 API 则显式选择 `HybridSearchWithRerank`。阈值、重排模型来源和候选深度应以实际入口为准。

## 需要记住什么

简要复述：**先逐 KB 授权与校验向量空间，再限额/按模型复用 embedding、按租户和存储分组召回；向量原分、关键词必要时归一化、双路加权 RRF；可选先宽池重排再补父邻关系块**。`MatchCount` 非正默认、上限 `500`；不是所有搜索都跑 rerank，检索 API 未启用时没有模型重排。出错时区别权限/模型冲突、没有候选、重排模型降级。详细问答接入看[C08](C08-动态问答流水线.md)；口播见[Q5](../WeKnora/面经.md#q5-只有向量只有关键词或两路都有时检索和问答分别怎样变化)。

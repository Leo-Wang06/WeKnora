## 本课重点

一次“上传成功”只说明服务端接收文件并建立知识记录，后面还有异步解析、索引乃至附加处理。前端必须同时维护**HTTP 传输状态**与**后台解析状态**，否则进度到 100% 就误报可检索，或者用户点取消后实际服务端仍保存了文件。本课追踪文件从页面选择到队列、后端存储、任务入队、批量轮询的执行顺序，重点解释三并发与同库同大小冲突、取消的不可逆时刻、账号/空间切换与迟到响应隔离。

## 主链与职责

知识库页面把 `File`、相对路径、标签和解析选项送到 Pinia 的全局 `uploadTasks` store；store 包一层可注入 API 与计时器的 `createUploadTasks`；队列最多同时传 3 个文件，上传进度映射为 waiting/uploading/saving；服务端先校验知识库写权限、大小及格式，算 hash 去重，存原文件并持久化 `parse_status=pending` 的知识记录，最后投递异步处理任务。HTTP 返回知识 ID 后，前端归类为 uploaded 而**非 ready**，按知识库聚合知识 ID 请求解析状态；页面刷新事件节流，未结算的失败项保留以供重试。真实索引结果属于服务端解析任务，不能由浏览器网络字节数推断。

## 源码阅读

1. **入口与所有权。** 读 [`useUploadTasksStore()`](../../frontend/src/stores/uploadTasks.ts#L10-L47)：它存在于全局 store，导航离开知识库页后仍能继续传；把上传 API、按 ID 批查状态、`knowledgeFileUploaded` 页面事件和 `auth.user.id + effectiveTenantId` 注入核心。读 [`createUploadTasks()`](../../frontend/src/stores/uploadTasksCore.ts#L23-L111)：并发 3、每 3000ms 查询、每请求最多 40 ID、同时最多 4 个查询，列表中途刷新节流 2000ms，结束事件 150ms 合并；watch 分开监听账号与空间身份，一旦换主体同步 dismiss，避免旧主体队列被新主体看到。
2. **传输队列。** 读 [`createUploadQueue()` 的 pump 和 transfer](../../frontend/src/stores/uploadQueue.ts#L92-L181)：状态在原 reactive 数组原地更新；同一知识库、相同文件大小暂不同时上传，以便服务端顺序写入后 hash 查重看得到前一条记录，但相同大小不等同内容相同，真正判重由服务端 hash 完成。返回结果经 [`classifyUploadResult()`](../../frontend/src/stores/uploadTasksState.ts#L217-L236) 划分成功、`duplicate_file` 与失败。服务端返回成功后标记 `uploaded`、保存知识 ID 和 `pending`/响应中的解析状态，并开启状态轮询。
3. **取消、重试和轮询。** 读 [`itemPhase()` 和 `needsParsePolling()`](../../frontend/src/stores/uploadTasksState.ts#L30-L82)：上传字节发送完但服务端尚未响应的 `saving` 不可视为完成；parse `finalizing` 已可检索，仍继续轮询至 completed。读 [`cancel()`/`retry()`](../../frontend/src/stores/uploadQueue.ts#L204-L237)：未开始或仍在发送的传输可中断，saving 不允许取消，失败/取消的 File 尚在时可重排；不能在保存阶段假装 abort 就能回滚服务器。读 [`pollNow()`](../../frontend/src/stores/uploadQueue.ts#L254-L304)：按 KB 分组、40 个 ID 分片、四并发，单次查询失败下轮再试；连续 3 次**成功查询却缺失**才判 deleted。再读 [`clear()` 的 generation](../../frontend/src/stores/uploadQueue.ts#L308-L333)：丢弃队列显示、取消尚在发送的请求、让保存中请求完成；旧代际回调不得写入新队列，落库成功时仍通知列表刷新。
4. **服务端拆阶段。** 先看 [`CreateKnowledgeFromFile()` 的权限与文件限制](../../internal/handler/knowledge.go#L313-L359)：只允许 KB owner 或 Admin/Editor；在 multipart 解析前限制请求体大小，非法 JSON 于 HTTP 边界直接返回错误。接着看 [文件 hash 去重和空间存储配额](../../internal/application/service/knowledge_create.go#L96-L140)、[文件名/路径校验和待解析记录](../../internal/application/service/knowledge_create.go#L154-L197)、[存储文件后持久化 DB 行及失败清理](../../internal/application/service/knowledge_create.go#L206-L227)。最后读 [投递 Asynq 异步任务](../../internal/application/service/knowledge_create.go#L234-L305) 与 [HTTP 成功响应](../../internal/handler/knowledge.go#L435-L460)。

## 机制与边界

普通路径：进度事件到达 100% 时进入 `saving`，表示浏览器请求体发完，服务端可能正在算 hash、保存文件与 DB 行；响应成功给知识 ID 以后才是 `uploaded`，后台处理状态 pending → processing → finalizing/completed，只有后两者被 UI 视为 ready，其中 finalizing 的附加摘要、问题或图谱增强仍可继续运行。`parse_status=failed` 进入 failed，不把网络成功当成解析成功；重复文件返回 409 携已有知识 ID，UI 展示 duplicate，也不作为本次新文件 ready。API 响应的 `200 success` **不是已经建立索引**：服务端文档入队失败会标记知识处理失败但仍返回 `knowledge,nil`，因为文件已被保存；UI 需依赖状态查询，而不是靠 HTTP 码猜测最终结果。

错误与取消各有独立语义：超出限额、类型不支持、JSON 错误或 KB 无写权限在保存之前拒绝；文件已存但 DB 行持久化失败时用 `context.WithoutCancel(ctx)` 尝试删掉孤儿文件，这里的清理是补偿，不应声称事务化原子。客户端在 `saving` 阶段即使关闭面板，也不能保证远端不生成记录，所以 `clear()` 只切断旧队列写回，并在迟到成功时触发 KB 列表刷新。解析轮询的单次网络失败不等于知识已删除；要三次成功查询均缺行才显示 deleted。换账号或工作空间时丢弃本地队列是界面隔离，不是服务器上的上传任务取消或权限撤销。

## 需要懂什么

**背压不是“所有文件并发越大越快”。** 三个传输槽限制服务器 hash/存储负载，同 KB 同大小串行只是辅助后端去重；状态请求按 KB 分组、按 40 ID 拆包且只允许四个请求在途，是为 URL 长度和数据库连接数设上界。**两阶段状态机是用户可信反馈。** `loadedBytes` 表示进度显示尺度，`sentBytes` 是实际传出的字节，`saving` 是不可轻率取消的服务器窗口；它们均不能证明检索可用。**generation 是本地生命周期屏障。** 旧批次可自然结束，但迟到结果不应重新占用新账号的面板或覆盖新批次；服务器最终状态仍要靠刷新和解析状态接口找回。

## 需要记住什么

- 从页面 `File` → 全局 Pinia → 3 并发传输 → 服务器 hash、文件、DB pending 行 → Asynq 处理 → 3 秒批量轮询；`200 ≠ ready`。
- `saving` 不取消；失败/取消仅在浏览器仍持 File 时重试，关闭或换身份只撤销本地队列，不能宣称服务端上传被回滚。
- 真实 duplicate 由后端内容 hash 决定，最终 ready 由解析状态而非上传进度决定。阅读 [Q4](../WeKnora/面经.md#q4-文件传完以后怎样把索引和-wiki-后续任务做成可观察可恢复的流程) 时重点描述这两种边界。
